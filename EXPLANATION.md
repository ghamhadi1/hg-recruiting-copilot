# EXPLANATION: what I built, and why

This document explains every part of the HG- AI Recruiting Copilot in plain language: what it does, how it does it, and why I chose that approach. For setup and testing, see [START_HERE.md](START_HERE.md).

---

## 1. The goal in one sentence

A non-technical recruiter can ask Slack a question, trust the answer, and approve in one click. Meanwhile the system writes the job description, reads every CV (even scanned ones), picks the best 5 candidates with honest reasons, and runs outreach that stops when people reply. **Nothing is ever sent without a human clicking Approve.**

## 2. The big picture

There are five building blocks, each doing the job it is best at:

| Block | Job | Why this tool |
|---|---|---|
| **n8n** (9 workflows) | The "conductor": receives events, calls the AI, talks to Slack, GHL and Gmail | Required by the brief. Visual, so a non-developer can follow each step |
| **OpenAI** | Writes JDs, reads scanned CVs, extracts profiles, understands questions, scores candidates | You already had a key; one provider covers text + vision + embeddings |
| **Supabase** | Stores everything; does search and all the "must never go wrong" rules | Postgres gives atomic rules (no double emails) and pgvector gives semantic search, in one free database |
| **Slack** | Where the recruiter asks and approves | The brief's audience lives in Slack; buttons = one-click approval |
| **GoHighLevel** | The candidate pipeline | Required by the brief; where the agency already manages contacts |
| **Portal (Vercel)** | Overview: roles + shortlists, pipeline, CV health, test score, activity | Needs to be online and readable without Slack |

## 3. The test data (`data/`)

- **5 call transcripts** written to be realistic and messy: a founder talking from his car, a client who changes her mind ("part-time… no wait, full-time"), notes typed in fragments, auto-transcripts with wrong speaker labels, and a private aside ("don't tell them that") that must not end up in the job description.
- **60 CV files for 55 fictional people**, generated by `data/generator/generate_cvs.py` from the persona list in `personas.py`:
  - Mixed PDF and Word, 3 different layouts each, different section names ("Work History", "Toolbox", "About me"), different date formats, contact details in a Word table (hard to extract), phone numbers written differently.
  - **1 scanned CV** (`Scan_0007.pdf`): a picture of a page with no text layer, slightly rotated, blurred, with speckles.
  - **3 people who appear twice**: Omar (PDF + Word, email in different capitals, phone written differently), Bilal (Word + PDF, email in CAPITALS), Rania (two byte-identical files with different names).
  - **2 people with an updated CV**: Lina (new job + n8n skill in 2026) and Layla (became a real-estate transaction coordinator in 2026).
  - **Near-misses on purpose**: Karim has 2.5 years of GHL (the question asks for 3+), Tariq has only "basic" Arabic, Hana speaks Japanese but has 2 years of Salesforce, not 10.
  - All emails use reserved `example.com/.net/.org` domains, so nothing can ever reach a real person.
- **2 extra broken files** (`data/hard_cases/`): a corrupt PDF and a blank scan, to prove unreadable files are flagged.
- **`ground_truth.json`**: who is who, which file is current. Used to write the 10 test questions.

**Why I generated them with a script instead of asking a chatbot:** the right answers to the test questions have to be known for certain. Because I control every fact, the test page can grade the bot automatically.

## 4. The database (`supabase/schema.sql`)

Tables (all prefixed `hg_`): `candidates`, `cvs` (every file ever received, with a status), `cv_chunks` (searchable pieces with embeddings), `roles`, `searches`, `shortlist`, `outreach`, `events` (activity log), `settings`, `eval_questions`, `eval_runs`.

**Why the important rules live in the database (SQL functions):** they must be correct even when two things happen at once. For example, a recruiter double-clicks Approve, or two sequencer runs overlap. A database function runs as one locked step, so:
- `hg_ingest_cv` decides **new / duplicate / replaced / older** in one go.
- `hg_role_decide` only accepts a decision while the JD is still pending, so a second click does nothing.
- `hg_candidate_decide` + `hg_start_outreach` can never create two email sequences for the same person and role.
- `hg_claim_due_outreach` "claims" the emails to send with a lock, so no email is sent twice.
- `hg_mark_reply` stops the sequence the moment a reply is seen.

**Security:** Row-Level Security is switched on with no rules, which means the public key can read nothing. Only the secret service key (kept in n8n and Vercel) can, and the functions are locked to that key too.

## 5. The workflows (`n8n/workflows/`)

I wrote the workflows as readable source (`n8n/src/build_workflows.py` + one `.js` file per Code node) and generate the JSON from it. **Why:** hand-editing big n8n JSON files is error-prone. This way every piece of logic is in a normal file that can be tested (`tests/test_code_nodes.js`), and the wiring is checked by `tests/lint_workflows.py`.

| Workflow | What it does |
|---|---|
| **HG- 00 Error Alerts** | If any workflow fails, posts 🚨 in Slack with a link to the failed run, so nothing fails silently |
| **HG- 01 Transcript to JD** | Transcript → OpenAI (strict JSON) → saves the role → posts to Slack with Approve / Request changes / Reject. Also handles "rewrite with feedback" (v2, v3…) |
| **HG- 02 CV Ingest** | File → text (PDF reader / Word unzip) → if no text and it's a PDF, the OpenAI vision model reads it (OCR) → if still nothing: **flag as unreadable** + Slack alert → otherwise extract profile → embeddings → database dedup/replace → Slack note when an updated CV replaced an old one |
| **HG- 03 Candidate Search API** | Question → structured requirements → hybrid search → AI scoring → **code guard** → top 5 + Slack buttons. Used by Slack, the portal, the auto-shortlist and the test page, so all four always give the same answer |
| **HG- 04 Slack Commands** | `/find …` and `/jd …`. Answers Slack within 3 seconds ("Searching…"), then posts the result |
| **HG- 05 Slack Buttons** | Every button: approve/reject/change JD, approve/reject candidate. Approve candidate → GHL contact + opportunity → queue outreach |
| **HG- 06 Outreach Sequencer** | Every 5 minutes (and right after an approval): re-checks the approval, checks the Gmail thread for a reply, then sends email 1, follow-up 2 (day 3) or follow-up 3 (day 7) in the same thread |
| **HG- 07 Reply Watcher** | Every 2 minutes: looks at every active email thread. A message we didn't send = a reply → stop, GHL stage "Replied", Slack 📬 |
| **HG- 08 Test Runner** | Asks the bot the 10 test questions and grades the answers |

## 6. How the "brain" makes trustworthy recommendations

This is the heart of the brief ("trust the answer", "never invents a candidate", "names the CV").

1. **Understand the question.** OpenAI turns "who has 3+ years of GHL and speaks Arabic?" into: skill GoHighLevel (synonyms GHL, HighLevel), minimum 3 years, required; language Arabic, required.
2. **Find possible people (hybrid search).** The database returns the best ~20 active CVs by **keyword hits** (exact tools like "QBO", "n8n") **plus meaning** (vector similarity, e.g. "books for dental offices" ≈ "bookkeeping for clinics"). **Why both:** keywords alone miss paraphrases, and vectors alone sometimes miss exact tool names.
3. **Score them.** OpenAI scores **only those people**, using the rubric (must-haves 50 · experience 20 · nice-to-haves 15 · language/location 15). For each person it writes 2 lines plus an **exact quote** from that person's CV.
4. **Check the AI's work with plain code (the guard).** This step doesn't use AI, so it can't make things up:
   - Any person not returned by the database is **deleted** (so the AI cannot invent anyone).
   - Each person appears **once**.
   - A **required language** must be in their profile, and "basic" doesn't count.
   - A **required skill** must be in their CV, and if a minimum number of years was asked, their years must reach it.
   - The **quote must really be in their CV**.
   - Fail any check → score capped at 59.
5. **Decide honestly.** Only scores of 60+ are recommended (top 5). If nobody reaches 60, the bot says **"No good match"** and shows the closest people with their exact gaps, without Approve buttons.
6. **Always name the source.** Every result carries the CV file name. It's stored in the shortlist, shown in Slack and the portal, and checked by the test page.

**Why a guard instead of just a better prompt:** prompts reduce mistakes but can't guarantee anything. The guard turns the most important promises into rules the code enforces.

## 7. CVs: duplicates, updates and unreadable files

- **Reading:** PDFs are read as text, and Word files are unzipped and their XML read (that also catches text inside tables). If a PDF has almost no letters, it's a scan, so the PDF goes to the OpenAI vision model to transcribe.
- **Unreadable:** if a file is corrupt, empty or an unsupported type, it's **stored with status "unreadable" and the reason**, a ⚠️ Slack alert is posted, and it shows in red on the portal's CV page. It is never silently skipped.
- **Same person?** Same email (ignoring capitals), otherwise same phone (last 9 digits, ignoring formatting), otherwise same normalised name.
- **Which CV wins?** The newer one, judged by the "last updated" date in the CV or the most recent job date. If the dates are equal, text similarity decides: ≥ 0.75 = the same CV in another format (duplicate), < 0.75 = a different CV (the newer upload wins). **I calibrated 0.75 on the real files** (`tests/calibrate_similarity.py`): same CV in another format scores 0.84–0.91, an updated CV 0.61–0.68, a different person 0.35.
- **Old CV:** kept for history (status "superseded") but its searchable pieces are deleted, so it can never be cited again.

## 8. Approvals: the "nothing reaches anyone" rule

| Moment | Gate |
|---|---|
| JD to client | Only after **Approve** on the JD in Slack. Reject sends nothing; Request changes creates a new version that needs approval again |
| Candidate outreach | Only after **Approve for outreach** on that candidate, for an **approved** role |
| Each email | The sequencer re-checks, right before sending, that the role and candidate are still approved and the sequence is still active |
| Double clicks | Database locks make the second click a no-op ("already approved") |
| Testing | **Test mode** (on by default) sends every email to *your* inbox as `you+hg-c12@gmail.com`, per the sandbox rule "only message yourself" |

## 9. GoHighLevel pipeline: my stage choice

`Approved → Outreach Sent → Replied → Screening Call → Submitted to Client → Placed / Not a Fit`

**Why:** it follows the real recruiting flow. The copilot moves cards automatically up to **Replied**, the point where a human must take over. The later stages are human decisions, so recruiters move those cards in GHL. Contacts and opportunities are named `HG- …` and tagged `HG-candidate` / `HG-role-<id>`, so they're easy to find and never confused with other people's sandbox data.

## 10. Outreach emails

Three short emails: an intro that uses the AI's first reason line ("Your background stood out: 5 yrs GoHighLevel, 120+ workflows"), a bump on day 3, and a polite close on day 7. They're sent through the Gmail API so follow-ups stay **in the same email thread**. That lets the system detect a reply reliably: any message in the thread that we didn't send.

## 11. The portal (`portal/`)

Pages: **Roles** (with a "new role from transcript" form), **Role detail** (JD, shortlist with score bar, 2 lines, quote, 📄 CV file, decision, outreach progress, Stop button), **Pipeline** (live from GHL, falling back to the copilot's own records), **CVs** (counts, a red box for unreadable files, the status of every file, upload), **Test** (10 questions, right answers, bot answers, score /10, run button, "try your own question"), and **Activity** (audit log).

**Why plain HTML + Vercel functions instead of a framework:** there's no build step that can break, it loads fast, and the code is easy to read. **Security:** the browser only talks to `/api/*`, and the keys stay in Vercel. There's a password login with a signed HttpOnly cookie. All CV text is escaped before it's shown, so a malicious CV can't inject code into the page.

## 12. The test (10 questions)

Each question targets a hard case (`eval/questions.json`): years thresholds, language filters, the scanned CV, duplicate people, updated CVs, similar-but-wrong tools, and a question with **no** right answer. A question passes only if every expected person is in the top 5, no wrong person is, nobody appears twice, every result names a CV file, and updated people cite their **new** CV.

## 13. How I tested without your accounts

I couldn't log into your services from here, so I tested everything that can be tested offline:
- **21 automated tests** run the real Code-node files with realistic inputs (`node tests/test_code_nodes.js`): invented candidates dropped, duplicates removed, years/language rules, fake quotes caught, Word tables read from the real generated CVs, OCR fallback, unreadable flagging, Slack verification, double-click handling, reply detection, email threading, the test grading and the JD format. **Result: 21/21 passed.**
- **Portal security test**: no data without login, forged cookies rejected, secure cookie flags. **Passed.**
- **Workflow lint**: every node reference in all 9 workflows exists and runs before the node that uses it. **Passed.**
- **SQL**: the whole schema parses with Postgres's own parser (pglast). This caught and fixed one real bug before you ran it.
- **Portal preview** with fake data, screenshotted to check the layout.

**Not tested yet (needs your accounts, see START_HERE Part E):** the live calls to OpenAI, Slack, GHL, Gmail and n8n. They're built to the official APIs, and the setup script's `check` command verifies each connection first.

## 14. Costs

Everything runs on free tiers except OpenAI usage. Loading 60 CVs plus a few dozen searches and the test runs costs roughly $0.50–$1.50 with `gpt-4.1-mini`. The model can be changed in `hg_settings.openai_model` without touching any workflow.

## 15. Known limits and what I'd do next

- GHL can't create pipelines by API, so it's a one-time manual step.
- The n8n demo server is shared, so webhook paths use the unique prefix `hg-p3-` to avoid clashes.
- Bulk-loading 60 CVs takes ~10–15 minutes because each one is read by AI (on purpose, for quality).
- Next steps: Slack's signing-secret check (stronger than the verification token), and a "book the screening call" step that offers Calendly/GHL calendar slots in the reply.
